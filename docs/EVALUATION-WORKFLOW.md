# Private evaluation workflow

Evaluation is an explicit admin operation. No collection, model download or paid inference runs as part of setup, CI or proof registration.

1. Select retained offer/image associations through `/v1/admin/evaluations`. Choose development/holdout assignments by seller and reused-image family. Duplicate image checksums are rejected.
2. Annotate visible florist types and assessable categories before starting inference. Record independent reviewers, including a second review for at least 20% of the eventual 100-image set. Annotation updates use expected versions and preserve private history. Seller-group identity is derived from the advertising account.
3. Explicitly queue the dataset. The worker executes independently checkpointed evaluation graphs with a $0.10 per-image allowance and the shared $100 monthly reservation ceiling. A primary joint pass, at most one bounded regional escalation and a separate image-only pass use the same recognition code/configuration as production. Image-only calls receive no conversation context. Neither evaluation path can commit listings.
4. Inspect item/job states. Completed call receipts survive crashes; uncertain dispatches require explicit admin replay. Re-queuing a paused/failed evaluation does not reset its job or authorize a paid replay. Missing credentials, media or source evidence are explicit failures.
5. Download private JSONL through the authenticated export endpoint, or run `python -m bouquetbrowse.cli evaluation-export --dataset-id ID`. CLI exports are confined to owned, ignored `.data/evaluations` files. Source expiry suppresses annotations/proofs and queues their file deletion. Copies manually downloaded elsewhere are operator-managed and must follow the same retention rules.
6. Stage the completed dataset and inspect the existing audited pilot proof report. Synthetic or under-sampled datasets cannot pass the real-data gate. Category support remains specific to taxonomy, graph behavior, prompt, preprocessing and model configuration. Approval is a separate, active-admin attestation of permitted data and joint reference review. Correcting annotations revokes its prior proof.

CLI `evaluation-status --dataset-id ID` reports versions, item states and measured costs. `evaluation-run --dataset-id ID --expected-version N` explicitly queues the reviewed batch. Windows workers handle `evaluation-graph` alongside offer jobs; PostgreSQL owns recurring checkpoints. Tests use in-memory checkpoints and fictional model responses.

Item latency measures successful processing steps, including local CV and cache reads; failed/crashed attempt wall time is not silently added to successful trial latency. Individual paid-call receipts also retain provider-call latency. Cost is the actual settled ledger for that evaluation execution; reused receipts incur no new billed amount. Report cache/recovery conditions when interpreting measurements.

Reviewed product crops receive their own association/checksum/region/model-bound SigLIP vectors. Whole-collage vectors cannot substitute for crops. No weights are downloaded until an explicitly configured vision worker is run.

For the twenty-conversation proof, use the general conversation explorer to choose ten distinct seller-rooted and ten buyer-request conversations. Independently record each candidate's expected advertising account, abstention and commercial price/count/fulfillment evidence with two reviewers. `POST /v1/admin/evaluations/conversation-references` accepts those manually authored `commercial_reference` prices/claims and produces deterministic signatures for the existing conversation proof staging endpoint. It never copies current model interpretations into the reference answers. Source-version quotes and price basis must be retained in the authored reference; schema and examples are available in the generated API contract. Joint review and real-data approval remain separately required.
